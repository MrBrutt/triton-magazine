# «Тритон»: сайт журнала

Сайт журнала студентов Международной гимназии Сколково: [triton-skolkovo.ru](https://triton-skolkovo.ru).
Хостинг GitHub Pages, ветка `main`, корень репозитория. Сборщика нет: браузер получает файлы как они лежат в репозитории.

## Как устроен сайт

| Файл | Что в нём |
| --- | --- |
| `app.js` | весь публичный сайт: данные, адреса, шаблоны страниц, читалка PDF, поиск |
| `admin.js` | редакция (`/admin/`): вход, выпуски, объявление. Загружается только на `/admin/` |
| `app.css` | все стили |
| `data/issues.json` | сохранённая копия выпусков из базы |
| `tools/build_pages.py` | собирает HTML-страницы, `sitemap.xml`, `robots.txt`, `rss.xml`, WebP-обложки |
| `tools/fetch_issues.py` | скачивает выпуски из базы в `data/issues.json` |
| `covers/N.jpg`, `covers/N.webp`, `covers/N-360.webp` | обложки номеров |
| `index.html`, `issues/…`, `about/`, `admin/`, `404.html`, `rss.xml`, `sitemap.xml` | **собираются скриптом**, руками не править |
| `CNAME`, `.nojekyll`, `google2b801f514098efe5.html` | домен, отключение Jekyll, подтверждение Search Console. Не трогать |

### Как страница попадает на экран

1. В HTML уже лежит готовая вёрстка страницы. Её собирает `build_pages.py` из `data/issues.json`
   по тем же шаблонам, что в `app.js`. Поисковики и превью в мессенджерах видят текст сразу,
   а для каждой страницы есть разметка schema.org (`Periodical`, `PublicationIssue`, хлебные крошки).
2. `app.js` берёт ту же копию `/data/issues.json` и рисует страницу заново. Разметка совпадает,
   поэтому DOM остаётся прежним (функция `setHtml`): ничего не мигает и не сдвигается.
3. После загрузки страницы `app.js` читает выпуски из Firestore через REST API, без SDK Firebase.
   Если в базе что-то поменялось, страница перерисовывается.
4. Если база недоступна, сайт работает на сохранённой копии и ещё несколько раз тихо пробует достучаться до базы.

SDK Firebase с `gstatic.com` подгружается только в редакции (`/admin/`): там он нужен для входа и записи.

Адреса: `/`, `/issues/`, `/issues/N/`, `/issues/N/read/` (читалка; файла нет, отдаёт `404.html`, страницу рисует `app.js`),
`/about/`, `/admin/`. Все остальные адреса показывают `404.html`.

## Как добавить номер

1. **Номер в базе.** Войдите на [/admin/](https://triton-skolkovo.ru/admin/), нажмите «Добавить выпуск», заполните поля
   и вставьте ссылки на PDF и обложку в Google Диске. С этой минуты номер виден на сайте:
   его подтягивает `app.js` из базы.
2. **Копия данных.** Чтобы номер появился в готовых HTML-страницах (поиск, превью ссылок, работа без базы), обновите копию:
   ```sh
   python3 tools/fetch_issues.py
   ```
   Без доступа к базе можно вписать номер в `data/issues.json` руками, по образцу соседних записей.
3. **Обложка на сайте** (по желанию, но так быстрее, чем из Диска). Сохраните обложку как `covers/N.jpg`
   (ширина 540–640 px) и добавьте в `LOCAL_COVERS` в `app.js` строку `"id-файла-в-Диске": N`.
   WebP-версии `build_pages.py` сделает сам.
4. **Значения по умолчанию** (по желанию). Цвет шапки, содержание, цитату и английские тексты обычно задают в редакции.
   Если их нет в базе, они берутся из `DEFAULTS` в `app.js`.
5. **Страницы.** Пересоберите их и закоммитьте всё, что изменилось:
   ```sh
   python3 tools/build_pages.py
   git add -A && git commit -m "Номер N"
   ```

## Как обновить страницы

После **любой** правки `app.js`, `admin.js`, `app.css` или `data/issues.json`:

```sh
pip install Pillow            # один раз: размеры картинок для превью и WebP-обложки
python3 tools/build_pages.py
```

Скрипт обновляет версию файлов в адресах (`app.js?v=…`), чтобы браузеры не держали старый код,
и пересобирает все страницы. Повторный запуск без правок ничего не меняет: CI это проверяет.

Если меняете шаблон страницы в `app.js` (функции `vHome`, `vIssues`, `vIssue`, `vAbout`, `card`, `cover`, шапка, подвал),
поменяйте его и в `build_pages.py`. Тест `tests/prerender.spec.js` сравнит обе вёрстки и подскажет, где они разошлись.

## Локальный запуск и тесты

```sh
npm ci                          # только для тестов, сайту npm не нужен
npm run serve                   # http://127.0.0.1:4173/, отвечает как GitHub Pages
npx playwright install chromium # один раз
npm test                        # Playwright: компьютер и телефон
```

Тесты никогда не обращаются к боевому Firebase: `tests/fixtures.js` подменяет REST API Firestore данными
из `data/issues.json`, а SDK с `gstatic.com` — заглушками из `tests/stubs/`. Все остальные внешние запросы обрываются.
В заглушке входа работает только `editor@example.com` / `secret`.

Что покрыто: главная, список номеров и поиск, страница номера, читалка, «О журнале», 404, форма входа и
восстановление пароля, мобильное меню, работа без Firebase и без копии, обновление из базы, объявление,
совпадение готовой вёрстки с `app.js`, сдвиги вёрстки, schema.org, RSS, запасной JPG вместо WebP.

GitHub Actions (`.github/workflows/tests.yml`) на каждом PR и пуше в `main` запускает тесты и проверяет,
что `build_pages.py` ничего не меняет.

## Скорость

Lighthouse 13, мобильный профиль (симуляция медленного 4G и слабого процессора), сайт отдаётся с gzip, как на GitHub Pages:

| Страница | Performance | LCP | CLS |
| --- | --- | --- | --- |
| `/` | 100 | 1.5–1.9 с | 0 |
| `/issues/` | 99 | 2.1–2.3 с | 0 |
| `/issues/10/` | 99–100 | 1.7–2.1 с | 0 |
| `/about/` | 100 | 0.8 с | 0 |

Почему быстро: готовая вёрстка в HTML, обложки WebP по размеру экрана (`N-360.webp` для карточек),
нет 600 КБ SDK Firebase на публичных страницах, а база спрашивается уже после загрузки.
